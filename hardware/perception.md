# 摄像头、ToF 与后续感知规划

## 当前设备证据

- 已确认用户最终通过直连显示器进入系统；显示器输出与头部摄像头是两种不同设备。
- 摄像头具体型号、接口、设备节点、画面方向、分辨率和帧率没有本机实测记录。
- 用户询问过 ToF 接入，当前没有确认本机 ToF 型号、I²C 地址或测距结果，不能把仿真 ToF 当成已装硬件。
- 头部 IMU 的 I²C 扫描不是 ToF 验证，见 [IMU 记录](imu.md)。

## 项目现有接口

Studio 控制页预留视频模式，通过 mediad 的 WebRTC 信令连接摄像头；媒体服务是独立服务，不会因为页面存在就证明摄像头已经可用。视频连接失败应显示真实错误。

`microduck_rl/src/mjlab_microduck/sim/camera.py` 模拟头部摄像头画面；`sim/tof.py` 模拟 VL53L5CX 型 8×8 多区测距。它们由虚拟身体服务器使用，不是 A733 的摄像头或 ToF 硬件驱动。

当前行走、起身、翻滚、踢球等 RL 动作没有使用这些模拟图像/头部测距作为输入；不能仅因模型内有传感器，就宣称训练已有视觉避障。

## 用户讨论过的后续需求

这些是规划，不是本机已经实现的能力：

- YOLO 物体识别、人物检测与跟随。
- 多人场景保持指定目标，避免仅按“person 类别”跟随而切错人。
- 结合人脸/身份信息和音视频，判断当前说话者，再由用户或策略选择是否跟随。
- 说话者位置不固定，鸭子需要通过抬头、转头寻找目标。
- 接入 LLM 自主行动，并在控制页展示可解释的运行状态/任务过程；目前 Studio 只保留自主行动入口。
- 讨论过利用 A733 的 NPU，但本机推理后端、厂商 SDK、模型转换和性能没有验证结论。原项目面向 Radxa/Rockchip 的 NPU 配置不应直接当成 A733 的方案。

YOLO 的检测框、目标身份/跟踪、说话者判断、底层 RL 行走分别承担不同任务。未来若只让高层视觉产生速度/转向指令，可以复用运动策略；若让 RL 直接读图像或测距，需要另外设计观测、策略网络及训练任务。

待接入实体传感器时再补：准确型号、接线、电压、设备节点、校准、时间戳/坐标系、实际采样率与延迟、驱动和推理后端版本。
